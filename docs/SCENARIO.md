# 业务场景演示（电商商品知识库 RAG）

> 用途：面试演示脚本 + 业务价值论证。**对话内容基于 `eval/corpus/` 的真实事实**，
> 与系统实际能答/不能答的范围完全一致，不会出现"演示很美好、一问就穿帮"。
> ⚠️ 第四节的价值测算是**假设模型**，不是实测数据 —— 简历里不要写，除非真的做过试点。

---

## 一、业务背景（场景设定）

**公司**：星联商城 —— 自有品牌的 3C 数码 + 小家电 DTC 官方商城（14 个品类、约 60 个在售 SKU）。

**痛点**（按严重度排序）：

| # | 痛点 | 具体表现 | 代价 |
|---|---|---|---|
| 1 | **参数记不住** | 单个 SKU 有 10+ 参数（价格/电池/快充/接口/重量/质保），新品上架频繁，培训跟不上 | 新人上手慢，答错率高 |
| 2 | **政策类问题吃掉人力** | 退换货、运费、发票、积分、优惠券规则被反复问 | 高频重复劳动，占咨询量约三成 |
| 3 | **大促咨询量暴增** | 日常约 200 咨询/天 → 大促约 2000/天 | 排队时长从几十秒涨到数分钟，转化流失 |
| 4 | **答错参数要按承诺履约** | 客服口误"支持 150W 快充"（实际 100W），用户截图投诉 | 直接赔付 + 品牌信任损失 |
| 5 | **通用大模型不能直接用** | 会用"常识"补全参数，编造价格/续航/保修年限 | 法务与合规风险不可接受 |

**系统定位**：商品知识库问答助手 —— 严格基于官方知识库作答并展示引用片段，客服可一键核查后转发用户，
用户也可在前端自助提问。

---

## 二、角色与使用方式

| 角色 | 用在哪 | 依赖的系统能力 |
|---|---|---|
| 客服坐席 | 边接咨询边查答案，**先看引用再回复** | 单轮问答 + 结构化引文 + 检索过程可视化 |
| 客服主管 / admin | 上传新品资料与政策文档、维护知识库 | KB 管理（上传 → 异步入库 → 状态轮询 → 删除/重灌） |
| 终端用户 | 商城自助问答 | 多轮对话 + 歧义追问 + 无关问题兜底引导 |

## 三、真实演示（8 个片段，覆盖全部关键路径）

### 场景 1 · 参数查询（单事实单源）

```
用户：星澜 Buds Pro 的降噪深度是多少？
助手：星澜 Buds Pro 的降噪深度是 48dB。 [1]
       📎 引用：[1] 无线耳机.md › 星澜 Buds Pro（相关度 0.83）
```
**要点**：数字逐字出自知识库原文（提示词硬性要求），不是模型"回忆"的。

### 场景 2 · 跨文档比较（多源 + 表格）

```
用户：Buds Pro 和 Headphone Max 哪个续航更长？
助手：
| 型号 | 类型 | 降噪 | 续航 | 价格 |
|---|---|---|---|---|
| 星澜 Buds Pro | 入耳式真无线 | 48dB | 单次 8 小时 / 带盒 36 小时 | 899 元 |
| 星澜 Headphone Max | 头戴式 | 45dB | 单次 40 小时 | 1299 元 |
结论：单次续航 Headphone Max 更长（40h），但配合充电盒 Buds Pro 可达 36h 且更便携。 [1][2]
```
**要点**：答案是**依据检索片段拼装**的，两个来源都给编号，可逐条回查。

### 场景 3 · 政策类问答（跨文档 + 多源）

```
用户：退货运费谁承担？
助手：因商品质量问题产生的退换货运费由平台承担；无理由退货运费由买家承担。 [1]
       📎 引用：[1] 售后服务政策.md › 退换货政策
```

### 场景 4 · 多轮追问（指代消解 → query 改写）

```
用户：星辰 X1 Pro 的价格是多少？
助手：12GB+256GB 版本 4999 元，16GB+512GB 版本 5699 元。 [1]

用户：那它的电池容量呢？          ← 含指代，单看这句无法检索
助手：星辰 X1 Pro 的电池容量是 5500mAh，支持 100W 有线快充和 50W 无线快充。 [1]
```
**内部动作**：检索侧把「那它的电池容量呢？」改写成自包含 query
（`星辰 X1 Pro 的电池容量`）再检索 —— 对应 `app/rag/rewriter.py`
与评测用例 `cases_multiturn.jsonl::mt01`。

### 场景 5 · 歧义追问（不猜、不编）

```
用户：手机多少钱？                ← 命中品类但没指定型号
助手：您想了解哪款手机呢？😊 我这边有以下型号：
      星辰 X1 Pro / 星辰 X1 标准版 / 星云 Note 5 / 星云 Note 5 Pro / 星辰 X1 Lite。
      请告诉我具体型号，我再为您查询～
```
**要点**：规则 + 静态商品词典检测（`app/rag/clarifier.py`），**零 LLM 成本、确定性可单测**，
对应评测 `cases_clarify.jsonl`（F1 = 1.00）。追问一次后用户给出型号，
下一轮"多少钱"由改写器借助历史补全 —— 两个机制自然闭环。

### 场景 6 · 知识库没有 → 明确说不（**这是最值钱的演示**）

```
用户：星域 View 27 的响应时间是多少毫秒？
助手：抱歉，知识库中暂未收录该信息，无法准确回答。
```
**对比**：通用大模型会自信地编一个"1ms"。
这条对应评测用例 `golden.jsonl::q41`（不可答负例），
也是「不可答不编造率」指标要守住 1.00 的原因。

### 场景 7 · 完全无关 → 友好兜底 + 引导回流

```
用户：今天天气怎么样？
助手：我主要擅长电商商品咨询哦～😊 你可以问我某款商品的价格、参数或售后政策。
```
**要点**：不硬拒答（体验差），也不硬答（越界），而是**接住话题 + 说明能力边界 + 举例引流**。
（`OFFTOPIC_SYSTEM_PROMPT`）

### 场景 8 · 高风险推测类 → 严谨不越界

```
用户：这款空调一个月要多少电费？
助手：知识库未收录电费数据，无法准确回答（可提供已知参数：制冷量 3500W、一级能效 APF 5.27）。
```
**要点**：电费取决于使用时长与电价，属"可推测但不可知"，
系统选择**给已知参数、不替用户下结论** —— 这正是提示词第 3 条的作用。

## 四、业务价值测算（**假设模型，非实测**）

> 下面是**算法框架**，用来回答面试官"这东西值多少钱"。
> 里面的系数是我按经验设的**假设值**，必须用真实试点数据替换后才能写进简历。

| 指标 | 现状（假设） | 上线后（假设） | 算法 |
|---|---|---|---|
| 首答时长 | 约 3 分钟（人工翻资料 + 核对） | 约 20 秒（检索 1–2s + 人工核查引用） | 人工查找时间 vs 检索延迟 P50 |
| 单次咨询处理时长 | 基准 100% | 下降 30%–50% | 政策类问题几乎"复制即可用" |
| 参数答错率 | 有（口误/记错） | 显著下降 | 回答必须带引用，坐席可核对；不可答时明确说不 |
| 新人培训周期 | 约 2 周 | 约 3 天 | 知识在库里而不在脑子里 |
| 人力折算 | 100 坐席 × 200 咨询/天 | 等效节省 ≈ 20–40 人力 | 咨询量 × 时长降幅 ÷ 单人日产能 |

**怎么用这张表**：面试时说"我按这个模型估算了收益，但**没有真实试点数据，所以我不把它写成成果**"——
这比编一个"效率提升 40%"安全一百倍，而且显得你懂"没有度量就没有结论"。

## 五、为什么这个场景非 RAG 不可（方案对比）

| 方案 | 为什么不选 |
|---|---|
| 通用大模型直接答 | 会编造参数与政策（价格/保修年限），法务风险不可接受 |
| 微调（SFT）自有数据 | 知识一更新就要重训；**仍可能编造**；无法给出引用出处 |
| 关键词搜索 / 传统 FAQ | 用户问法千变万化，字面匹配命中率低；无法处理多轮与比较类问题 |
| **RAG（本方案）** | 知识随文档热更新（上传即入库）；答案附引用可核查；不可答时明确说不 |

## 六、场景 ↔ 评测用例对应关系（证明评测是业务驱动的）

| 业务场景 | 评测覆盖 |
|---|---|
| 参数查询（单事实） | `golden.jsonl` q01–q04、q27–q37（含新增品类） |
| 跨文档比较 / 多源 | q05、q14、q15（`FullCoverage@5` 专门守这类） |
| 政策类问答 | q07、q08、q38–q40 |
| 多轮指代追问 | `cases_multiturn.jsonl` mt01–mt08（`rewrite_hit_rate` + 帮倒忙率） |
| 歧义追问 | `cases_clarify.jsonl` cl01–cl10（F1 ≥ 0.90 门禁） |
| 不可答不编造 | `golden.jsonl` q21–q26、q41–q42（**不编造率 == 1.00 门禁**） |
| 引文可核查 | `citation_precision ≥ 0.95` 门禁 + 引文清洗夹具 |

## 七、面试演示脚本（3 分钟版）

1. **30 秒｜痛点一句**：自有品牌 60 个 SKU，客服用通用大模型答商品问题会编参数，
   答错要按承诺赔付 —— 所以需要一个"只依据官方资料说话、并且能给出处"的助手。
2. **60 秒｜现场跑 3 个问题**（按杀伤力排序）：
   - ① 「星域 View 27 的响应时间是多少毫秒？」→ **明确说不**（对比通用模型会编）
   - ② 「星辰 X1 Pro 的价格是多少？」→「那它的电池容量呢？」→ 展示**多轮改写**
   - ③ 「手机多少钱？」→ 展示**歧义追问**
3. **60 秒｜翻到评测**：42 条金标（含 8 条不可答负例）双层解耦评测；
   门禁化（阈值 + 退出码）；我修掉了判分器 fail-open 的缺陷并用故障注入回归。
4. **30 秒｜主动讲局限**：混合检索需要 Milvus Standalone，本地是 dense-only 基线；
   语料 20 chunks 偏小，金标要往 150 条扩。

**演示前检查清单**：`make eval-mock` 能跑通（零成本自检）→ 真实 key 有余额 →
演示用问题全部来自 `golden.jsonl`（已确认可答/不可答）→ 准备一个"知识库没收录"的问题作为压轴。
