## 一、v2 相对 v1 改了什么（每条都有明确动机）

| # | v1 的问题 | v2 的做法 | 影响 |
|---|---|---|---|
| 1 | **judge 解析失败默认判「通过」**（`grounded = True if grounded is None else grounded`）——判分器返回非法 JSON 时白送一个通过，指标被系统性高估且无人察觉 | 解析失败记为 `judge_error`，**从分子分母同时剔除**，并新增 `judge_coverage` 门禁 | 「判分器坏了」现在表现为**指标不可信 + 门禁红灯**，而不是虚假好成绩 |
| 2 | 指标全部依赖 LLM-judge（自评偏见：生成与判分同一个模型） | 新增两个**确定性指标**：`numeric_recall`（gold 数字命中率）、`citation_precision`（引文越界率） | 可与 judge 交叉验证：judge 说忠实、但 gold 数字一个没命中 → 人工复核 |
| 3 | 失败只有「通过/不通过」，无法定位环节 | 每题输出 `failure_type`：`retrieval_miss` / `retrieval_noise` / `generation_hallucination` / `answer_incomplete` / `judge_error` / `fabrication` | 失败可回流到具体环节（改检索 / 改提示词 / 改判分器） |
| 4 | 跑完只打印数字，**没有退出码** → 改了提示词看不出退化 | `eval/gate.py` 集中阈值 + `PASS/FAIL/SKIP` + `exit 1` | 评测变成 **CI 门禁**，可直接挡住退化 |
| 5 | 门控阈值 `GATE_THRESHOLD = 0.35` 是硬编码魔数，从未验证 | `eval/sweep.py` 扫描阈值，量化「可答保留率 vs 不可答拦截率」，输出 [SWEEP.md](SWEEP.md) | 阈值从「魔数」变成「有数据的决策」，并证明**不存在完美分离阈值** |
| 6 | `rewriter` / `clarifier` / `citation` 三个功能有代码、无数据 | `eval/features.py` 分别量化：多轮改写增益、歧义追问 F1、引文清洗夹具 | 面试被问「多轮改写效果如何」时有数字可答 |
| 7 | 语料 6 篇 / 10 chunks，`Recall@10` 恒等于 1（无区分度） | 语料扩到 **14 篇 / 20 chunks**；`retrieval.py` 增加**指标有效性自检**（top_k vs 语料规模） | 指标恢复区分度，且脚本会主动提示「这个指标本次没有区分度」 |
| 8 | RAG 核心路径零单测 | 新增 `test_retriever.py` / `test_pipeline.py` / `test_eval_metrics.py` | 门控、去重、上下文组装、指标计算都有回归保护（30 → **71** 个单测） |
| 9 | 评测必须联网 + 花 token，无法快速复跑 | `eval/fakes.py` 提供确定性替身 + `--mock` 模式 | 离线秒级跑通完整链路（入库→检索→门控→生成→判分→门禁→退出码） |

#### ⚠️ 读数须知：多项指标触顶（天花板效应）

Recall@5 = MRR = 忠实度 = 1.000 这类满分，**主要反映评测集难度不足，而不是系统完美**：

- 语料只有 20 chunks（14 篇文档），问题以单事实、单文档为主 → 检索很容易命中；
- 34 条可答问题的 gold 都在知识库里，生成又被约束在 context 内 → 忠实度自然高。

**真正有信息量的是这四项**：

1. **不可答不编造率 1.000（8/8）** —— 安全不变量，与语料大小无关（负例是知识库确实没有的信息）；
2. **引文准确率 1.000** —— 越界引用 0 处，引文白名单有效；
3. **门控扫描数据** —— 可答问题 top1 最低分 **0.581**、不可答问题 top1 最高分 **0.782**，区间重叠，
   **不存在完美分离阈值**；当前阈值 0.35 的不可答拦截率为 **0.000**，
   即「语义拒答完全由生成层承担」这句话有了数据支撑，而不再是一句声明；
4. **失败归因分布为空** —— 6 类失败本次都没出现；等语料变难，它才会开始产生价值。

### 3.4 混合检索实测（Zilliz Cloud 免费实例，2026-09-12）

> 背景：README / DESIGN 把「混合检索（dense + BM25 稀疏 + RRF 融合）」写成卖点，
> 但本地 Milvus Lite **不支持 sparse/BM25**，这条路径**从未被执行过**（典型的「宣称 vs 实测」缺口）。
> 本次接入 Zilliz Cloud 实测，脚本：`eval/hybrid_compare.py`，完整报告：[HYBRID.md](HYBRID.md)。

| 指标 | dense-only | dense+BM25(RRF) | 变化 |
|---|---|---|---|
| Recall@5 | 1.000 | 1.000 | +0.000 |
| Recall@K | 1.000 | 1.000 | +0.000 |
| FullCoverage@5 | 1.000 | 1.000 | +0.000 |
| Precision@5 | 0.251 | 0.230 | -0.021 |
| MRR | 1.000 | 1.000 | +0.000 |
| NDCG@K | 0.995 | 1.000 | +0.005 |

**结论：两者均触顶 —— 当前评测集无法区分优劣。**
这是 **ceiling effect（天花板效应）**：20 chunks 语料 + 单事实单文档问题，两种检索都容易命中。
**不能解读为「混合检索没用」，更不能写成「混合检索提升 X%」**（这个数字不存在）。
提高区分度的方案已写入 HYBRID.md 末节（扩语料至 100+ chunks、加型号密集查询、加同品牌干扰文档、改 chunk 级评测）。

**⚠ 过程中发现并修复 5 个隐藏缺陷**（详见 [BAD_CASES.md](../docs/BAD_CASES.md) #15 / #16）：

| # | 缺陷 | 症状 |
|---|---|---|
| 1 | 门控量纲错误：RRF 分数（0.01–0.03）被相似度阈值（0.35）过滤 | 混合检索**永远返回空** |
| 2 | BM25 输入字段缺 `enable_analyzer=True` | create_collection 被拒 |
| 3 | 稀疏索引 metric 误用 `IP`（BM25 输出字段必须用 `BM25`） | create_collection 被拒 |
| 4 | 集合含双向量字段时 dense 检索未指定 `anns_field` | search 报 ambiguous |
| 5 | pymilvus 2.6 把 `hybrid_search` 的 `rerank` 改名为 `ranker` | 调用 TypeError |

> 这 5 个缺陷有一个共同点：**都藏在「从未执行过的代码路径」里**。
> 本地 Milvus Lite 只支持 dense，所以混合检索分支从写下第一天起就没被跑过。

### 3.5 混合检索：扩充高干扰语料后的可分辨结果（2026-09）

> §3.4 的结论是"两者均触顶、无法分辨" —— 那是**天花板效应**（20 chunks 里取 top5 必然命中）。
> 为得到有区分度的结论，把语料扩到 **180 篇高干扰合成语料**（同品牌 12 个变体、型号名互为子串）
> + **172 条金标**，重新对比。完整报告：[HYBRID.md](HYBRID.md)；语料与金标：`eval/hard/`。

| 指标 | dense-only | dense+BM25(RRF) | 变化 |
|---|---|---|---|
| Recall@5 | 0.981 | **0.992** | +0.011 |
| Recall@K | 0.989 | **1.000** | +0.011 |
| FullCoverage@5 | 0.962 | **0.985** | +0.023 |
| MRR | 0.917 | **0.979** | **+0.061** |
| NDCG@K | 0.930 | **0.976** | +0.045 |

#### 增益来自哪一类查询（关键）

| 查询类型 | 题数 | dense R@5 | hybrid R@5 | dense MRR | hybrid MRR | ΔMRR |
|---|---|---|---|---|---|---|
| **基础型号（无后缀）** | 42 | 1.000 | 1.000 | **0.788** | **0.968** | **+0.181** |
| 短后缀（Pro/Lite/SE…） | 30 | 1.000 | 1.000 | 0.983 | 0.983 | 0 |
| 长后缀（Pro Max/Ultra） | 20 | 1.000 | 1.000 | 0.975 | 0.975 | 0 |
| 相邻变体比较（需两篇都命中） | 40 | 0.938 | **0.975** | 0.975 | 0.988 | +0.013 |
| 总体 | 132 | 0.981 | 0.992 | 0.917 | 0.979 | +0.061 |

**两个结论**：
1. 增益集中在**「查询名是其他文档名子串」**的场景（基础型号查询 MRR 0.788 → 0.968）；
2. 在名称独特的查询上两种方法**完全无差异**（0.983 vs 0.983、0.975 vs 0.975）——
   **BM25 不是普遍更优**，这个"无差异"同样是结论的一部分。

#### 机制：dense 的系统性偏差

逐题分析（`analyze_failures.py`，hybrid 赢 18 题 / dense 赢 4 题 / 平 110 题）显示失败模式高度一致：

| 查询 | dense 排第一 | 正确答案 |
|---|---|---|
| 星辰 X1 的处理器 | `星辰X1Standard.md` | `星辰X1.md` |
| 星辰 X2 的快充 | `星辰X2Lite.md` | `星辰X2.md` |
| 星云 Fold 的屏幕 | `星云FoldStandard.md` | `星云Fold.md` |
| 星澜 Buds 的防水等级 | `星澜BudsStandard.md`（排第 3） | `星澜Buds.md` |

**规律**：查询的型号名是其他文档名的子串时，dense 会系统性偏好**更长/后缀更全**的文档
（长名称的语义向量"覆盖更全"，与短查询余弦相似度反而更高）；而用户要的恰恰是精确那个型号。
BM25 的词面精确匹配天然没有这个偏好 —— **"标准版"在语义上≈"基础款"，这正是语义相似性的反噬**。

#### 诚实边界

1. **语料是合成的**（180 篇由模板程序化生成），模拟的是"同品牌多型号、参数相近"的干扰结构，
   **不能替代真实商品资料验证**。
2. Recall@5 仍接近触顶（0.981 / 0.992），差异主要体现在 **MRR / NDCG 这类排序敏感指标**。
3. reranker 未启用；跑在 Zilliz Cloud 上，与自建 Standalone 可能有差异。
4. **两轮实验的路径本身是结论的一部分**：先发现"测不出来"，再把任务变难，最后解释差异来源。

| 歧义追问 F1 | ≥ 0.90 | 该追问就追问，不该追问别打扰 |

## 五、诚实边界（面试别踩坑）

1. **金标规模仍偏小**：42 条 vs 设计目标 ~150 条。当前价值在**分类覆盖**（可答/不可答/多轮/多源/政策数值）
   与**评测机制**（fail-closed、门禁、归因），不在统计置信度。继续扩充应遵循「每发现一个真实失败 → 加一条用例」。
2. **语料 20 chunks 仍不大**：`Recall@10` 的区分度已经恢复（top_k=10 < 20），但要让 Recall 更稳，语料应继续扩到 30+ chunks；
   `retrieval.py` 的「指标有效性自检」会自动提示何时又失去区分度。
3. **忠实度是区间不是点**：LLM-judge 有噪声（v1 同批答案两次判分 20/20 vs 19/20）。
   v2 已用 `judge_coverage` 把「判分器失效」从「通过」里剥离，但**同模型自评偏见仍在**——
   彻底解决需换判分模型或多模型投票（未做）。
4. **混合检索已实测，且已测出可分辨差异**（见 §3.4 与 §3.5）：
   - 第一轮（20 chunks）：两者双双触顶 1.000 —— **天花板效应**，测不出差异；
   - 第二轮（180 篇高干扰合成语料 + 172 条金标）：**MRR 0.917 → 0.979（+0.061）**、
     Recall@K 0.989 → 1.000；增益集中在**基础型号查询**（MRR 0.788 → 0.968）。
   - 过程中修复该分支 5 个隐藏缺陷；但**语料为合成生成，不能替代真实语料验证**。
5. **门控不负责语义拒答**：`sweep.py` 的数据证明可答与不可答的分数区间**重叠**，
   不存在完美分离阈值；「不编造」由生成层双提示词保证，不是门控的功劳。
6. **mock 模式数字无意义**：`--mock` 验证的是评测机器能跑、门禁会红，不代表 RAG 质量。
