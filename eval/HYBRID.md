# 混合检索实验：从「天花板效应」到「可分辨差异」

> 脚本：`eval/hybrid_compare.py`（总体对比）、`eval/breakdown_by_type.py`（分组归因）、
> `eval/analyze_failures.py`（逐题胜负）、`tools/gen_hard_corpus.py`（高干扰语料生成）
> 语料与金标：`eval/hard/`（180 篇合成语料 / 172 条金标）
> 日期：2026-09

---

## 一、实验动因：第一轮为什么失败

第一轮（14 篇语料 / 20 chunks）的结论是：

> dense 与 hybrid 的 Recall@5 / MRR **双双击穿 1.000** —— 无法分辨优劣。

这是**天花板效应**：20 个 chunk 里取 top5 几乎必然命中，任何检索策略都能满分。
**问题不在检索策略，在评测集难度不足。**

于是有了第二轮：把语料扩到 180 篇，并**刻意构造高干扰密度**。

---

## 二、结论先行（第二轮）

**172 条金标（132 可答 + 40 不可答），180 篇语料**

| 指标 | dense-only | dense+BM25(RRF) | 变化 |
|---|---|---|---|
| Recall@5 | 0.981 | **0.992** | +0.011 |
| Recall@K | 0.989 | **1.000** | +0.011 |
| FullCoverage@5 | 0.962 | **0.985** | +0.023 |
| MRR | 0.917 | **0.979** | **+0.061** |
| NDCG@K | 0.930 | **0.976** | +0.045 |

**hybrid 在全部 5 项指标上一致更优。**

> 注意：Recall@5 仍接近触顶（0.98 / 0.99），因为 top-5 足够容纳正确答案。
> **真正暴露差异的是排序敏感指标 —— MRR（+0.061）与 NDCG（+0.045）。**
> 换句话说：两种方法都能"找到"，差别在"排第几"。

---

## 三、关键：增益来自哪一类查询

只看总体会以为是"普遍小幅提升"，分组后才发现**增益高度集中**：

| 查询类型 | 题数 | dense R@5 | hybrid R@5 | dense MRR | hybrid MRR | ΔMRR |
|---|---|---|---|---|---|---|
| **基础型号（无后缀）** | 42 | 1.000 | 1.000 | **0.788** | **0.968** | **+0.181** |
| 短后缀（Pro/Lite/SE…） | 30 | 1.000 | 1.000 | 0.983 | 0.983 | **0** |
| 长后缀（Pro Max/Ultra） | 20 | 1.000 | 1.000 | 0.975 | 0.975 | **0** |
| **相邻变体比较（需两篇都命中）** | 40 | 0.938 | **0.975** | 0.975 | 0.988 | +0.013 |
| 总体 | 132 | 0.981 | 0.992 | 0.917 | 0.979 | +0.061 |

**两个明确结论**：

1. **增益集中在"查询名是其他文档名子串"的场景** —— 基础型号查询上 dense 的 MRR 只有
   **0.788**，hybrid 达到 **0.968**（+0.181）。这是全部增益的主要来源。
2. **在名称独特的查询上，两种方法完全无差异**（短后缀 0.983 vs 0.983、长后缀 0.975 vs 0.975）。
   **这个"无差异"同样是结论的一部分** —— 它说明 BM25 不是普遍更优，
   只在特定查询形态下有效。

## 四、机制解释：dense 的系统性偏差

逐题分析（`analyze_failures.py`）显示失败模式**高度一致**：

| 查询 | dense 排第一 | 正确答案 | hybrid |
|---|---|---|---|
| 星河 洗衣机 的价格 | `星河洗衣机Standard.md`（标准版） | `星河洗衣机.md` | ✅ 排第一 |
| 星辰 X1 的处理器 | `星辰X1Standard.md` | `星辰X1.md` | ✅ 排第一 |
| 星辰 X1 Pro Max 的快充 | `星辰X1ProMaxPlus.md` | `星辰X1ProMax.md` | ✅ 排第一 |
| 星河 净化器 的质保年限 | `星河净化器Standard.md` | `星河净化器.md` | ✅ 排第一 |

**规律：当查询的型号名是其他文档名的"子串"时，dense 会系统性偏好那个更长/后缀更全的文档。**

**原因**：
- 长名称文档的语义向量"覆盖更全"，与短查询的余弦相似度反而更高；
- 而用户要的是**精确的那一个型号** —— 查"X1"就是要 X1 基础款，不是 X1 标准版；
- BM25 的**词面精确匹配**没有这个偏好：查询与文档标题完全一致时得分最高。

**这在真实电商场景里是高价值发现**：型号目录有 12 个变体时，
"星辰 X1 多少钱"（最自然的用户问法）恰恰是 dense 最容易答错的那一类。

## 五、实验设计：如何让语料"真的难"

结论能否成立，取决于语料难度是否真实。设计要点：

| # | 设计 | 为什么 |
|---|---|---|
| 1 | **1 型号 = 1 文档** | 最初我把 3 个相邻型号放进同一篇文档 → doc-level 检索必然命中，什么都测不出来。**这是第一版设计缺陷** |
| 2 | **文档结构完全同构** | 都是「型号名 + 同一组属性」，只有型号名与参数值不同 → 语义向量高度重合 |
| 3 | **属性值取自小池子** | 电池只有 6 个候选值 → 大量文档共享同一数值，只能靠型号名区分 |
| 4 | **变体后缀只差一个 token** | Pro / Pro+ / Pro Max / Pro Max+ / Lite / SE / Ultra / 标准版 |
| 5 | **查询分布按真实用户问法** | 用户更常问基础型号，而基础型号名是其他 11 个变体的子串 → 干扰最强，故过采样（42 条） |
| 6 | **固定随机种子、程序化生成** | 完全可复现，且 **0 token 成本**（语料不让 LLM 生成） |

## 六、诚实边界

1. **语料是合成的**：180 篇由模板程序化生成（品牌 × 产品线 × 变体组合），**不是真实商品资料**。
   它模拟的是"同品牌多型号、参数相近"的干扰结构，**不能替代真实语料验证**。
2. **Recall@5 仍接近触顶**（0.981 / 0.992），差异主要体现在 MRR / NDCG。
   若要进一步拉大区分度，可缩小 top_k 或继续增加同族变体数。
3. **短后缀/长后缀两组无差异**：BM25 的收益不是普适的。
4. **reranker 未启用**：本次是 dense vs dense+BM25(RRF)，不含 bge 重排。
5. **环境差异**：跑在 Zilliz Cloud（AWS 法兰克福）上，索引参数与自建 Milvus Standalone 可能有差异；
   结论不能直接外推到所有部署形态。

## 七、两轮实验对照（简历叙事）

| | 第一轮 | 第二轮 |
|---|---|---|
| 语料 | 14 篇 / 20 chunks（真实手写） | 180 篇（合成，高干扰） |
| 金标 | 42 条 | 172 条 |
| 结果 | 两者均 1.000，**无法分辨** | dense MRR 0.917 vs hybrid 0.979（**+0.061**） |
| 收获 | 认识到**天花板效应** | 定位到**增益的具体来源与机制** |

**这条路径本身就是工程能力的体现**：不是直接甩一个好看的数字，
而是**先发现"测不出来"，再去把任务变难，最后解释差异从何而来**。

## 八、复现

```bash
# 1. 生成高干扰语料与金标（0 token 成本，固定种子可复现）
python tools/gen_hard_corpus.py eval/hard

# 2. 入库 + 双模式总体对比
cd backend
python ../eval/hybrid_compare.py --corpus ../eval/hard/corpus --golden ../eval/hard/golden.jsonl \
    --collection eval_hard_kb --report ../eval/HYBRID.md --reingest

# 3. 分组归因（增益来自哪类查询）
python ../eval/breakdown_by_type.py --golden ../eval/hard/golden.jsonl --collection eval_hard_kb

# 4. 逐题胜负与失败模式
python ../eval/analyze_failures.py --golden ../eval/hard/golden.jsonl --collection eval_hard_kb
```

**成本实测**：入库 180 篇 embedding ≈ 0.02 元；对比实验仅需 embedding（不调生成），
两轮不到 **0.1 元**；耗时约 10 分钟（含跨境网络延迟）。
